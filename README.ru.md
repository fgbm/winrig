Полная документация — на https://fgbm.github.io/winrig/ru/.

**MCP-сервер для удалённого администрирования Windows-хостов по WinRM/NTLM, написанный на Rust.** Диагностируйте, изучайте и администрируйте любой Windows-хост в домене AD из Cursor, Claude Code, Codex, opencode или любого клиента MCP (Model Context Protocol). Введите пароль AD один раз через `winrig setup`. Сервер хранит пароль только как аутентифицированный шифртекст. Ключ остаётся у клиента. Сервер никогда не пишет пароль в конфигурацию клиента открытым текстом.

`winrig` — преемник Python-проекта `win-mcp-server` на Rust. Он сохраняет те же доменные правила, границы модулей и контракты инструментов. Проект поставляет один статический бинарь без контейнера и интерпретатора. Сервер работает либо как HTTP-сервис (`winrig serve`), либо как локальный stdio-процесс (`winrig stdio`).

- **Мало памяти, один бинарь**: один release-бинарь, без runtime, без контейнера. Резидентная память держится около 11 МиБ после старта и повторных запросов на компьютере разработки (`VmRSS` из `/proc`).
- **37 инструментов** плюс `write_file`, когда оператор его включит: файловая система, службы, реестр, журналы событий, сертификаты, процессы, сеть, запланированные задачи и прочее. Эти инструменты уже портированы. В Python-версии `win-mcp-server` были передача файлов (копирование/перемещение/переименование/архивы), `invoke_http_request` и инструменты SFTP. Эти инструменты пока не портированы.
- **Один процесс на профиль**: `winrig setup` создаёт шифрованный профиль. Напечатанный токен профиля — единственный ключ, и `setup` показывает его один раз. Второй процесс на том же профиле отказывает в старте и указывает на HTTP-режим.
- **Два секрета, по одному на запрос**: запрос аутентифицируется либо `WINRIG_AUTH_TOKEN` (путь по заголовкам с `X-AD-User`), либо токеном профиля. Токен профиля задаёт идентичность и заставляет сервер игнорировать `X-AD-*`.
- **Никаких секретов на диске**: ни учётных данных в конфигурациях, ни в журналах. В файле профиля лежит только аутентифицированный шифртекст.

## Почему Rust

- Один release-бинарь, `cargo build --release`; без Docker, без Python, без pip.
- Память ограничена и мала. Одна длинная команда не может заблокировать другой запрос, потому что транспорт асинхронный.
- Клиент WinRM/NTLM, протокол MCP и HTTP-стек — зрелые крейты, поэтому проект несёт доменную логику, а не протокольную обвязку. См. `docs/adr/0007-rust-stack.md`.

### Active Directory — решено, но не построено

Ни одного из этих инструментов в бинаре сегодня нет. Раздел фиксирует решение (ADR-0014, срезы W19–W21), а не возможность. Он здесь потому, что само отсутствие вводит в заблуждение. Агент видит WinRM и хост в домене и предполагает, что каталог доступен. Но каталог не доступен.

Почему так: NTLM даёт удалённому хосту network logon без делегируемых учётных данных. Поэтому запрос к каталогу с хоста — члена домена — второй хоп к контроллеру домена. Такой запрос отказывает с `An operations error occurred`. `run_command` это не изменит: он работает в той же сессии с тем же токеном. Есть маршрут, который работает и вовсе не требует делегирования: **подключитесь к самому контроллеру домена**. Там запрос локален. Сейчас AD касается только `get_security_context`, и лишь потому, что доменные группы лежат в токене сессии.

Планируется в срезе W19. Только чтение. Опрос через `System.DirectoryServices`, а не командлетами RSAT. Те ходят в ADWS и требуют установленного модуля и запущенной службы:

| Инструмент | Описание |
|------|-------------|
| `get_ad_object` | Один пользователь, группа или компьютер: состояние учётной записи, сроки пароля, последний вход, DN, OU |
| `get_ad_membership` | Членство в обе стороны, при необходимости вложенное |
| `find_ad_objects` | Поиск по имени или `sAMAccountName` с потолком результатов |
| `get_ad_domain_info` | Домен, лес, уровни функционирования, роли FSMO, контроллеры, доверия, сайты, парольная политика и PSO |
| `get_ad_health` | Партнёры репликации и отставание, службы NTDS/DNS/ADWS/W32Time, состояние SYSVOL |
| `get_ad_stale_objects` | Залежавшиеся пользователи и компьютеры по `lastLogonTimestamp` и `pwdLastSet` |

Запись в каталог (срезы W20–W21) решена в том же ADR и намеренно оставлена за пределами первой волны. По умолчанию она будет выключена за `WINRIG_ALLOW_AD_WRITE`. Она будет подтверждать каждый вызов с DN объекта. Она будет отвергать защищённые объекты и встроенные группы до обращения к сети. Она будет принимать ровно один явно названный объект на вызов и никогда фильтр. Атрибут пройдёт только через `WINRIG_AD_WRITABLE_ATTRIBUTES`. Текущий бинарь не читает ни одну из этих переменных. Проект не планирует менять топологию домена или леса: захват ролей FSMO, чистку метаданных, принудительную репликацию. Проект не планирует и удаление объектов каталога.

### Модифицирующие операции (все требуют подтверждения)

| Инструмент | Описание |
|------|-------------|
| `restart_service` / `stop_service` / `start_service` | Управление службами с состоянием до и после |
| `kill_process` | Принудительное завершение процесса по PID |
| `set_registry` | Запись значения реестра с показом старого и нового |
| `delete_file` / `delete_directory` | Удаление с запросом подтверждения; инструмент отвергает защищённые пути, в том числе по фактическому расположению системы на хосте |
| `flush_dns` | Очистка кэша DNS-клиента |
| `write_file` | Запись файла с заменой целиком. **Выключен по умолчанию**: задайте `WINRIG_ALLOW_FILE_WRITE=true`, иначе сервер не объявляет инструмент и вызвать его нельзя |

`write_file` отвергает защищённые пути тем же списком, что охраняет удаление. Он отвергает существующий файл, если не задан `overwrite`. Перед подтверждением хост сообщает, куда на самом деле ляжет файл и где у него стоят системные каталоги (`SystemRoot`, `ProgramFiles`, `ProgramFiles(x86)`, `ProgramData`, профили пользователей). Поэтому Windows на томе, отличном от `C:`, защищена так же.

Инструмент отвергает путь с 8.3-именем (`PROGRA~1`): сравнить его со списком может только хост. Административный общий ресурс `\\host\C$\...` инструмент проверяет как `C:\...`. Общие ресурсы `ADMIN$`, `PRINT$`, `SYSVOL` и `NETLOGON` защищены целиком. Точки повторной обработки (junction и symlink) в родительских каталогах цели инструмент не раскрывает (ADR-0015).

Содержимое идёт кусками по ~2 КБ, потому что командная строка WinRS ограничена примерно 8191 символом. Поэтому инструмент годится для конфигураций и скриптов, а не для больших объёмов. Остаток ограничивает `WINRIG_MAX_WRITE_BYTES` (по умолчанию 64 КиБ). Куски ложатся во временный файл рядом с целевым файлом. Переименование заменяет целевой файл. Сбой на середине оставляет существующий файл нетронутым.

Это ограничение на длину относится к командной строке, а не к выводу. Скрипт, который не влезает в одну команду, запишите через `write_file` и затем запустите по пути. Команда остаётся короткой, каким бы длинным ни был скрипт.

## Установка

К каждому релизу приложены готовые бинари для Linux, macOS и Windows. Рядом с каждым архивом лежит контрольная сумма `sha256`. Linux-бинари собраны со статической линковкой (musl), поэтому не требуют определённой версии glibc.

```bash
# Замените версию и таргет на свою платформу.
curl -LO https://github.com/fgbm/winrig/releases/latest/download/winrig-v0.2.0-x86_64-unknown-linux-musl.tar.gz
curl -LO https://github.com/fgbm/winrig/releases/latest/download/winrig-v0.2.0-x86_64-unknown-linux-musl.sha256
sha256sum -c winrig-v0.2.0-x86_64-unknown-linux-musl.sha256
tar xzf winrig-v0.2.0-x86_64-unknown-linux-musl.tar.gz
install -m 0755 winrig ~/.local/bin/winrig
```

Архивы называются `winrig-v<версия>-<таргет>`, где таргет — один из `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin` или `x86_64-pc-windows-msvc`. На macOS архив `aarch64` — для Apple Silicon, `x86_64` — для Intel. Подходят и `tar`, и `unzip`, потому что в архиве рядом с бинарём лежат `LICENSE` и `README.md`.

Чтобы собрать из исходников, см. [Быстрый старт](#быстрый-старт).

## Быстрый старт

Соберите один раз:

```bash
cargo build --release
```

Создайте шифрованный профиль. Команда читает пароль без эха и печатает токен профиля ровно один раз:

```bash
./target/release/winrig setup corp --user 'DOMAIN\user'
```

Команда печатает токен профиля и JSON-определение MCP-сервера. Либо вставьте определение в клиент вручную, либо дайте `setup` записать его за вас. `setup` обновляет конфигурацию клиента на месте и не трогает чужие записи:

```bash
./target/release/winrig setup corp --user 'DOMAIN\user' --write-config opencode --scope global
./target/release/winrig setup corp --user 'DOMAIN\user' --write-config claude-code --scope project
```

`--write-config` требует уровень. Передайте `--scope global` для пользовательской конфигурации или `--scope project` для текущего репозитория. Без флага `setup` спрашивает в терминале. В неинтерактивном запуске (скрипт, CI) `setup` отказывает и указывает на `--scope`.

По умолчанию сервер подключается только к loopback (`localhost`, `127.0.0.0/8`, `::1`). Хосты, к которым он может ходить, задаёт `--allowed-hosts`: список через запятую; элемент с ведущей `.` — суффикс домена; `*` — любой хост. `setup` пишет его в запись клиента как `WINRIG_ALLOWED_HOSTS`, а повторный `setup` без флага эту переменную убирает:

```bash
./target/release/winrig setup corp --user 'DOMAIN\user' --write-config claude-code --scope global --allowed-hosts '.corp.example,web-01'
```

Запись называется так же, как та, что уже обслуживает этот профиль. Поэтому повторный `setup` обновляет её на месте, а не добавляет вторую. Это важно: две записи на один профиль поднимают два процесса. Второй теряет блокировку профиля и выходит, а клиент сообщает лишь `MCP error -32000: Connection closed`. Когда профиль ещё никем не обслуживается, имя — `winrig`. `--server-name` задаёт его явно.

Поддерживаемые клиенты: `opencode`, `claude-code`, `codex`, `cursor`. Project-уровень находит ближайший каталог-предок с `.git` (с откатом к текущему каталогу) и пишет в `<root>/opencode.json`, `<root>/.mcp.json`, `<root>/.codex/config.toml` или `<root>/.cursor/mcp.json`. Global-уровень сохраняет пользовательские пути.

Для opencode `setup` пишет токен профиля в отдельный файл `0600` и подставляет его ссылкой `{file:...}`. Поэтому токен профиля никогда не лежит внутри конфигурации клиента. На project-уровне этот файл живёт в `WINRIG_STATE_DIR`, а не в репозитории. Для остальных трёх клиентов токен профиля идёт в конфигурацию клиента значением. На project-уровне такой файл обычно коммитится, поэтому `setup` печатает предупреждение, а `winrig` выставляет файлу `0600` на Unix.

Запустите сервер в одном из двух режимов:

```bash
# Локальный stdio-процесс для одного клиента (токен профиля приходит из окружения клиента)
WINRIG_TOKEN='<токен из setup>' ./target/release/winrig stdio --profile corp

# HTTP-сервис на 127.0.0.1:8005/mcp для нескольких проектов
WINRIG_TOKEN='<токен из setup>' ./target/release/winrig serve --profile corp

# Переопределить адрес из командной строки (важнее окружения)
./target/release/winrig serve --profile corp --port 9000 --host 0.0.0.0

# Передать секреты аргументами вместо окружения (важнее окружения)
./target/release/winrig serve --profile corp --token '<токен из setup>'
./target/release/winrig serve --auth-token '<общий секрет>'
```

Флаги `--token` и `--auth-token` перекрывают `WINRIG_TOKEN` и `WINRIG_AUTH_TOKEN`. Секрет, переданный аргументом, виден в списке процессов. Поэтому предпочитайте окружение или конфигурацию клиента, где это возможно.

Определение сервера, которое печатает и записывает `setup`, включает `WINRIG_TOKEN`, `WINRIG_PROFILE_DIR` и `WINRIG_STATE_DIR`. Поэтому клиент находит профиль даже при нестандартных каталогах.

Чтобы оставить путь по заголовкам вместо профиля, задайте общий секрет и обойдитесь без профиля:

```bash
echo "WINRIG_AUTH_TOKEN=$(openssl rand -base64 32)" >> .env
set -a; . ./.env; set +a
./target/release/winrig serve
```

В HTTP-режиме привязка по умолчанию — `127.0.0.1:8005`, конечная точка — `/mcp`. Серверу нужен хотя бы один секрет. Он отказывает в старте, если нет ни токена профиля, ни `WINRIG_AUTH_TOKEN`.

## Профили

```bash
winrig setup corp --user 'DOMAIN\user'   # создать; печатает токен профиля один раз
winrig setup corp --user 'DOMAIN\user' --overwrite   # заменить существующий профиль
winrig list                              # таблица: NAME, USER, PATH; секретов нет
winrig list --json                       # те же данные в JSON
winrig rotate corp                       # перешифровать под свежим токеном профиля
winrig forget corp                       # удалить профиль (идемпотентно)
```

Файл профиля — `corp.json` в каталоге профилей. В нём лежат версия формата, каноническое имя учётной записи, соль HKDF-SHA256, nonce XChaCha20-Poly1305 и шифртекст. Имя учётной записи связано как associated data. На Unix права файла — `0600`, права каталога — `0700`. Более широкие права дают предупреждение, а не отказ. Журнал различает неверный токен профиля и повреждённый файл, но клиенту оба отвечают 401. Если `WINRIG_AUTH_TOKEN` совпал с токеном профиля, старт отказывает.

Учётная запись имеет вид `DOMAIN\user`, например `contoso\alice`. Деление для NTLM повторяет `spnego` (движок `requests-ntlm`, который использовал Python-сервер): система делит имя по первому обратному слэшу. UPN (`user@realm`) или голое имя остаются целыми с пустым доменом. Профиль хранит учётную запись в каноническом нижнем регистре, и то же значение уходит на хост. NTLM сам приводит имя пользователя к верхнему регистру, когда строит хеш. Поэтому регистр домена на результат не влияет.

Один процесс на профиль. Lock-файл в каталоге состояния профиля останавливает второй процесс на том же профиле. Второй процесс отказывает и указывает на HTTP-режим. Изменения профиля на диске вступают в силу при следующем старте. Пароль профиля по-прежнему подчинён блокировке учётной записи AD. Если его отвергли дважды в разных окнах блокировки, профиль отказывает до перезапуска процесса. Выполните `setup` заново.

## Конфигурация

Вы настраиваете всё через окружение. Файла конфигурации нет. Файл профиля — не конфигурация, а хранилище шифртекста (ADR-0009).

| Переменная | По умолчанию | Назначение |
|----------|---------|---------|
| `WINRIG_AUTH_TOKEN` | — | Общий секрет для пути по заголовкам; запрос обязан предъявить его как `Authorization: Bearer <token>` или `X-MCP-Token`. Не обязателен, когда используется токен профиля |
| `WINRIG_PROFILE` | — | Имя профиля; опускается, когда профиль ровно один, обязательно при нескольких |
| `WINRIG_TOKEN` | — | Токен профиля, напечатанный `setup`; обязателен в stdio-режиме и для пути профиля в HTTP |
| `WINRIG_PROFILE_DIR` | каталог конфигурации ОС | Переопределяет каталог профилей (`~/.config/winrig` на Linux) |
| `WINRIG_STATE_DIR` | каталог состояния ОС | Переопределяет **корень** каталога состояния; `winrig` сам добавляет имя профиля, поэтому блокировки и журналы по умолчанию ложатся в `<WINRIG_STATE_DIR>/<профиль>`. Указывайте корень, а не каталог самого профиля, иначе блокировка уедет на уровень в сторону от того места, где её ждёт конфигурация клиента |
| `WINRIG_BIND_HOST` | `127.0.0.1` | Адрес, который слушает HTTP-сервер |
| `WINRIG_PORT` | `8005` | Порт, который слушает HTTP-сервер |
| `WINRIG_PASSWORD_TTL_SECONDS` | `3600` | Сколько живёт закэшированный пароль AD без использования; по истечении пароль стирается, а сессии пользователя закрываются. `0` отключает истечение. На пути по заголовкам кэш не открывает сессию: `connect` требует `X-AD-Password` в каждом запросе. В режиме профиля повторный ввод TTL не вызывает никогда |
| `WINRIG_LOG_DIR` | каталог состояния профиля | Каталог для `winrig.log` и `winrig-audit.log`. Сервер создаёт каталог `0700`, а файлы `0600` |
| `WINRIG_LOG_LEVEL` | `INFO` | Уровень журнала сервера (`DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`). Уровень не влияет на аудит, аудит сервер пишет всегда |
| `WINRIG_LOG_MAX_BYTES` | `10485760` | Размер, при котором журнал ротируется |
| `WINRIG_LOG_BACKUP_COUNT` | `5` | Сколько ротированных файлов хранится на журнал |
| `WINRIG_AUDIT_MAX_OUTPUT_CHARS` | `2000` | Сколько символов stdout/stderr на вызов сервер сохраняет в аудите |
| `WINRIG_AUDIT_LOG_BODY` | `1` | Значение `0`, `false`, `no` или `off` пишет только метаданные вызова: ни текста команды, ни вывода |
| `WINRIG_CONFIRM_TIMEOUT_SECONDS` | `300` | Сколько модифицирующий инструмент ждёт ответа подтверждения, прежде чем отказать (fail-closed) |
| `WINRIG_LOCKOUT_ATTEMPTS` | `3` | Число неудачных попыток пароля AD, после которого сервер не предъявляет пароль до конца окна блокировки |
| `WINRIG_LOCKOUT_WINDOW_SECONDS` | `1800` | Сколько секунд сервер не повторяет отвергнутый пароль |
| `WINRIG_SECRET_REDACT_MIN_LENGTH` | `4` | Кратчайший секрет, который сервер вырезает из **ответа агенту**. Аудит и файлы журнала вырезают секреты любой длины, безусловно |
| `WINRIG_ALLOWED_HOSTS` | *(пусто)* | Список разрешённых хостов через запятую. Пустое значение разрешает только loopback-литералы: `localhost`, `127.0.0.0/8`, `::1`; сервер не разрешает имена через DNS. Отдельный элемент `*` разрешает любой хост. Остальные записи — точное имя хоста или IP (без учёта регистра) или суффикс, если запись начинается с `.`. Неверный элемент (например `*.corp.example`) отказывает старту. Хост с портом, путём или `@` в `connect` сервер отвергает при любом списке. `setup --allowed-hosts` пишет значение в запись клиента |
| `WINRIG_ALLOW_INSECURE_TLS` | `false` | Принимает ли сервер `verify_cert=false`. По умолчанию сервер отвергает такой вызов до любой сетевой активности; `true` разрешает самоподписанные сертификаты |
| `WINRIG_ALLOW_FILE_WRITE` | `false` | Существует ли инструмент `write_file`. Пока значение `false`, сервер удаляет инструмент из роутера: не объявляет его и вызвать его нельзя |
| `WINRIG_MAX_WRITE_BYTES` | `65536` | Наибольшее содержимое, которое принимает `write_file`, в байтах. Сервер отвергает его до сетевой активности. Значение не может быть меньше одного куска в 2000 байт |
| `WINRIG_SFTP_CRED_TTL_SECONDS` | `3600` | Зарезервировано под инструменты SFTP (пока не портированы). Сервер разбирает и проверяет значение при старте |

### Безопасность транспорта

`winrig` отдаёт открытый HTTP на `/mcp`, TLS-слушателя в бинаре нет. **Bearer-токен теперь ключ: кто его перехватит, тот достигнет сервера и расшифрует пароль AD.** Не привязывайтесь к не-loopback адресу без TLS-терминирующего обратного прокси впереди (nginx, Caddy или ingress). Адрес по умолчанию — `127.0.0.1` именно поэтому.

Многопользовательское развёртывание предполагает, что прокси аутентифицирует клиентов. Прокси передаёт заголовки `Authorization`, `X-AD-User` и `X-AD-Password` без изменений. Удалённый участок WinRM отдельный: используйте `use_ssl` или порт 5986, когда хоп до Windows-хоста должен быть шифрованным. Не включайте `WINRIG_ALLOW_INSECURE_TLS=true`, если самоподписанный сертификат не выбран сознательно.

Список хостов по умолчанию пропускает только loopback. Иначе агент, получивший инструкцию из данных, мог бы подключиться к хосту атакующего и отдать ему NTLMv2-ответ доменной учётной записи.

Поверх открытого HTTP этот участок WinRM шифрован лишь частично. `winrm-rs` запечатывает SOAP-тела ключом сессии NTLM. Но ключа не существует, пока не завершится рукопожатие. Поэтому **первый** запрос на каждом новом соединении несёт своё тело открытым текстом рядом с сообщением Type 3. Запечатаны только последующие запросы на этом keep-alive соединении.

Для `winrig` первое тело — это shell `Create`, а не скрипт. Но если хост отвечает на незашифрованное сообщение пустым `HTTP 500` (`AllowUnencrypted=false`, умолчание Windows), он сразу отвергает этот запрос. Порт 5986 снимает и экспозицию, и отказ.

## Настройка клиента

Есть две формы запроса. С **токеном профиля** секрет — это токен профиля, а идентичность берётся из профиля, поэтому `X-AD-User` не нужен. С **общим секретом** запрос обязан нести `WINRIG_AUTH_TOKEN` и `X-AD-User`. Сервер проверяет токен прежде, чем доверяет `X-AD-User`: этот заголовок — ключ кэша паролей и сессий в памяти.

`WINRIG_AUTH_TOKEN` обязателен только на пути по заголовкам. `X-AD-Password` необязателен на уровне HTTP, но на пути по заголовкам обязателен для каждого `connect`. Закэшированный пароль по одному имени сессию не открывает, потому что `X-AD-User` может назвать любой держатель общего секрета. Уже открытая сессия исполняет команды без повторного пароля, пока не закрыта (ADR-0015). Пароль приходит заголовком, а не диалогом: `winrig` не запрашивает пароли через elicitation. Спецификация MCP исключает из elicitation секреты, а ревизия протокола `2026-07-28` убирает elicitation целиком (см. `docs/adr/0006-password-header-and-confirmation.md`).

Пути ниже — пользовательские, их записывает `--scope global`. При `--scope project` та же запись идёт в проектный файл, перечисленный в [«Быстром старте»](#быстрый-старт).

### opencode (`~/.config/opencode/opencode.json`)

`setup --write-config opencode --scope global` пишет этот файл. Токен профиля подставляется из приватного файла:

```json
{
  "mcp": {
    "winrig": {
      "type": "local",
      "command": ["/path/to/winrig", "stdio", "--profile", "corp"],
      "environment": { "WINRIG_TOKEN": "{file:~/.config/opencode/winrig-token}" },
      "disabled": false
    }
  }
}
```

### Claude Code

`setup --write-config claude-code --scope global` пишет блок `mcpServers` файла `~/.claude.json`. Эквивалент через CLI:

```bash
claude mcp add winrig -- /path/to/winrig stdio --profile corp
```

### Codex (`~/.codex/config.toml`)

`setup --write-config codex --scope global` пишет его:

```toml
[mcp_servers.winrig]
command = "/path/to/winrig"
args = ["stdio", "--profile", "corp"]

[mcp_servers.winrig.env]
WINRIG_TOKEN = "<токен из setup>"
```

### Cursor (`~/.cursor/mcp.json`)

`setup --write-config cursor --scope global` пишет блок `mcpServers`. HTTP-форма работает одинаково для любого клиента: направьте клиент на streamable-HTTP конечную точку и передайте `Authorization: Bearer <token>`.

Любой другой MCP-клиент работает так же. Либо используйте stdio-определение, которое напечатал `setup`, либо направьте клиент на HTTP-конечную точку. Передайте токен профиля в качестве bearer.

### Подтверждения на клиентах без elicitation

Модифицирующие инструменты получают подтверждение через MCP elicitation. Они **отказывают (fail-closed)**, когда клиент не может спросить. opencode 1.18.31 объявляет только `roots`. Поэтому модифицирующие инструменты отказываются там работать и говорят об этом, а не действуют без подтверждения. Инструменты только для чтения работают нормально. Замену канала (`input_required`, SEP-2322) проект отслеживает в `docs/ROADMAP.md` и `docs/QUESTIONS.md` Q-10.

## Журналирование

`WINRIG_LOG_DIR` хранит `winrig.log` и аудит `winrig-audit.log`. Сервер создаёт каталог `0700`, а файлы `0600`, и переприменяет права при каждой ротации.

Аудит записывает каждый вызов с текстом PowerShell и выдержкой из его вывода. В этом выводе могут быть содержимое файлов, данные реестра, списки учётных записей и сертификаты. Поэтому по умолчанию аудит пишет только первые `WINRIG_AUDIT_MAX_OUTPUT_CHARS` символов. Агент всё равно получает полный ответ.

Задайте `WINRIG_AUDIT_LOG_BODY=0`, чтобы писать только метаданные вызова. Отказ политики до обращения к хосту идёт отдельной записью `POLICY REFUSED`. Запись несёт пользователя, инструмент, код и причину. Отказ политики бывает при неразрешённом хосте, порте или TLS, при `connect` без `X-AD-Password` и на защищённом пути.

В stdio-режиме stdout несёт только JSON-RPC. Журнал сервера и аудит уходят в stderr и в каталог состояния профиля. Поэтому клиент, который запускает `winrig stdio`, никогда не видит строк журнала, подмешанных в протокол.

## Разработка

```bash
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
cargo deny check
cargo build --release
```

Закреплённый тулчейн лежит в `rust-toolchain.toml`. CI выполняет те же команды плюс `cargo-audit` и сборку на MSRV (`rust-version` в `Cargo.toml`). Живого Windows-хоста в окружении разработки нет. Тесты работают на фиктивном `WinRmTransport`, который записывает переданные ему команды, и сети не касаются. `tests/http_gate.rs` проверяет реальную обвязку axum+rmcp `/mcp`, а `tests/stdio_mode.rs` запускает настоящий бинарь поверх stdio. Канон проекта, требования, ADR и цикл ревью живут в `AGENTS.md` и `docs/`.

### Релизы

Релиз ставится так: поднимите `version` в `Cargo.toml`, добавьте соответствующую запись в `CHANGELOG.md` и отправьте тег `vX.Y.Z`. Тег запускает `.github/workflows/release.yml`. GitHub Release создаётся из записи changelog, а бинарь собирается под пять таргетов и прикладывается с контрольной суммой `sha256`. Workflow отказывает, если тег и версия в `Cargo.toml` расходятся.

| Workflow | Триггер | Что делает |
|----------|---------|--------------|
| `ci.yml` | каждый push и pull request | `fmt`, `clippy`, `test`, release-сборка, сборка на MSRV, `cargo-audit`, `cargo-deny` |
| `release.yml` | тег `vX.Y.Z` | пишет GitHub Release и загружает архивы платформ с контрольными суммами |
