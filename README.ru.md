Полная документация — на https://fgbm.github.io/winrig/ru/.

**MCP-сервер для удалённого администрирования Windows-хостов по WinRM/NTLM, написанный на Rust.** Диагностируйте, изучайте и администрируйте любой Windows-хост в домене AD из Cursor, Claude Code, Codex, opencode или любого клиента MCP (Model Context Protocol). Введите пароль AD один раз через `winrig setup`. Сервер хранит пароль только как аутентифицированный шифртекст. Ключ остаётся у клиента. Сервер никогда не пишет пароль в конфигурацию клиента открытым текстом.

`winrig` — преемник Python-проекта `win-mcp-server` на Rust. Он сохраняет те же доменные правила, границы модулей и контракты инструментов. Проект поставляет один статический бинарь без контейнера и интерпретатора. Сервер работает либо как HTTP-сервис (`winrig serve`), либо как локальный stdio-процесс (`winrig stdio`).

- **Мало памяти, один бинарь**: один release-бинарь, без runtime, без контейнера. Резидентная память держится около 11 МиБ после старта и повторных запросов на компьютере разработки (`VmRSS` из `/proc`).
- **43 инструментов** плюс `write_file`, `run_command`, `run_script`, файловые операции, `download_file` и `upload_file`, когда оператор их включит: файловая система, службы, реестр, журналы событий, сертификаты, процессы, сеть, запланированные задачи и прочее. Эти инструменты уже портированы. В Python-версии `win-mcp-server` были инструменты архивов (сжатие и распаковка), `invoke_http_request` и инструменты SFTP. Эти инструменты пока не портированы.
- **Один процесс на профиль**: `winrig setup` создаёт шифрованный профиль. Напечатанный токен профиля — единственный ключ, и `setup` показывает его один раз. Второй процесс на том же профиле отказывает в старте и указывает на HTTP-режим.
- **Два секрета, по одному на запрос**: запрос аутентифицируется либо `WINRIG_AUTH_TOKEN` (путь по заголовкам с `X-AD-User`), либо токеном профиля. Токен профиля задаёт идентичность и заставляет сервер игнорировать `X-AD-*`.
- **Никаких секретов на диске**: ни учётных данных в конфигурациях, ни в журналах. В файле профиля лежит только аутентифицированный шифртекст.

## Почему Rust

- Один release-бинарь, `cargo build --release`; без Docker, без Python, без pip.
- Память ограничена и мала. Одна длинная команда не может заблокировать другой запрос, потому что транспорт асинхронный.
- Клиент WinRM/NTLM, протокол MCP и HTTP-стек — зрелые крейты, поэтому проект несёт доменную логику, а не протокольную обвязку. См. `docs/adr/0007-rust-stack.md`.

### Active Directory — решено, но не построено

Ни одного из этих инструментов в бинаре сегодня нет. Раздел фиксирует решение (ADR-0014, срезы W19–W21), а не возможность. Он здесь потому, что само отсутствие вводит в заблуждение. Агент видит WinRM и хост в домене и предполагает, что каталог доступен. Но каталог не доступен.

Почему так: NTLM даёт удалённому хосту network logon без делегируемых учётных данных. Поэтому запрос к каталогу с хоста — члена домена — второй хоп к контроллеру домена. Такой запрос отказывает с `An operations error occurred`. `run_command` это не изменит: он работает в той же сессии с тем же токеном. Есть маршрут, который работает и вовсе не требует делегирования: **подключитесь к самому контроллеру домена**. Там запрос локален. Сейчас AD касается только `get_security_context`, и лишь потому, что доменные группы лежат в токене сессии.

Планируется в срезе W19. Только чтение. Опрос через `System.DirectoryServices`, а не командлетами RSAT. Те ходят в ADWS и требуют установленного модуля и запущенной службы:

| Инструмент | Описание |
|------|-------------|
| `get_ad_object` | Один пользователь, группа или компьютер: состояние учётной записи, сроки пароля, последний вход, DN, OU |
| `get_ad_membership` | Членство в обе стороны, при необходимости вложенное |
| `find_ad_objects` | Поиск по имени или `sAMAccountName` с потолком результатов |
| `get_ad_domain_info` | Домен, лес, уровни функционирования, роли FSMO, контроллеры, доверия, сайты, парольная политика и PSO |
| `get_ad_health` | Партнёры репликации и отставание, службы NTDS/DNS/ADWS/W32Time, состояние SYSVOL |
| `get_ad_stale_objects` | Залежавшиеся пользователи и компьютеры по `lastLogonTimestamp` и `pwdLastSet` |

Запись в каталог (срезы W20–W21) решена в том же ADR и намеренно оставлена за пределами первой волны. По умолчанию она будет выключена за `WINRIG_ALLOW_AD_WRITE`. Она будет подтверждать каждый вызов с DN объекта. Она будет отвергать защищённые объекты и встроенные группы до обращения к сети. Она будет принимать ровно один явно названный объект на вызов и никогда фильтр. Атрибут пройдёт только через `WINRIG_AD_WRITABLE_ATTRIBUTES`. Текущий бинарь не читает ни одну из этих переменных. Проект не планирует менять топологию домена или леса: захват ролей FSMO, чистку метаданных, принудительную репликацию. Проект не планирует и удаление объектов каталога.

### Модифицирующие операции (все требуют подтверждения)

| Инструмент | Описание |
|------|-------------|
| `restart_service` / `stop_service` / `start_service` | Управление службами с состоянием до и после. `stop_service` проверяет останов: ждёт `wait_seconds` (по умолчанию 15), читает состояние и события 7031/7034/7036 журнала System и сообщает ошибкой, если служба снова запустилась. При `disable=true` он задаёт тип запуска Disabled до останова |
| `set_service_start_type` | Задать тип запуска (Automatic, AutomaticDelayed, Manual или Disabled). Подтверждение показывает текущий и новый тип запуска. Инструмент отвергает службу, критичную для удалённого сеанса |
| `kill_process` | Принудительное завершение процесса по PID. Подтверждение показывает имя, путь к исполняемому файлу (без аргументов) и время запуска. Командная строка не читается, поэтому секрет в ней не утечёт (DR-4) |
| `set_registry` | Запись значения реестра. Старое и новое значения показаны только как `hidden`; подтверждение сообщает, есть ли старое значение и какого оно типа |
| `delete_file` / `delete_directory` | Удаление с запросом подтверждения; инструмент отвергает защищённые пути, в том числе по фактическому расположению системы на хосте. `delete_file` принимает список разрешённых путей `WINRIG_WRITE_ALLOW_PATHS`; рекурсивный `delete_directory` — нет (DR-6) |
| `flush_dns` | Очистка кэша DNS-клиента |
| `write_file` | Запись файла с заменой целиком. **Выключен по умолчанию**: задайте `WINRIG_ALLOW_FILE_WRITE=true`, иначе сервер не объявляет инструмент и вызвать его нельзя |
| `run_command` | Запуск произвольной команды PowerShell. **Выключен по умолчанию**: задайте `WINRIG_ALLOW_COMMAND_EXEC=true`, иначе сервер не объявляет инструмент и вызвать его нельзя. Подтверждение показывает полный текст команды. Сервер отвергает команду вне непустого `WINRIG_ALLOWED_COMMANDS` до сетевой активности |
| `run_script` | Запуск скрипта PowerShell длиннее одной командной строки WinRS. **Выключен по умолчанию**: задайте `WINRIG_ALLOW_SCRIPT_EXEC=true`, иначе сервер не объявляет инструмент и вызвать его нельзя. Сервер записывает скрипт во временный `.ps1` в каталоге временных файлов сеанса, читает файл и выполняет его текст как блок скрипта, затем пытается удалить файл. У скрипта нет `$PSScriptRoot`, нет `$PSCommandPath` и нет аргументов. Одно подтверждение покрывает всю операцию и показывает весь скрипт и его SHA-256. Список префиксов `WINRIG_ALLOWED_COMMANDS` не фильтрует скрипт |
| `copy_file` / `move_file` / `rename_file` / `create_directory` | Копирование, перемещение и переименование файла или каталога, а также создание каталога с родителями. **Выключены по умолчанию**: задайте `WINRIG_ALLOW_FILE_OPS=true`, иначе сервер не объявляет инструменты и вызвать их нельзя. Все четыре запрашивают подтверждение. Копирование каталога показывает счётчики и отвергает исходное дерево с символической ссылкой или junction. Перемещение на одном томе переименовывает; между томами копирует файл и удаляет источник, а перемещение каталога между томами отвергает (DR-6). Переименование принимает одно новое имя. Ни один из четырёх не заменяет существующий каталог, а существующая цель требует `overwrite` (кроме `create_directory`, который её отвергает). Цель подчиняется `WINRIG_WRITE_ALLOW_PATHS`; источник копирования может лежать в системном каталоге, потому что копирование только читает его |
| `download_file` | Копирование файла с хоста в локальный каталог передачи. **Выключен по умолчанию**: задайте `WINRIG_ALLOW_FILE_DOWNLOAD=true`, иначе сервер не объявляет инструмент и вызвать его нельзя. Инструмент читает файл на хосте окнами по 16 МиБ и пишет его в `WINRIG_TRANSFER_DIR`, и сверяет SHA-256 обеих сторон. Результат несёт имя, размер и хеш, а не содержимое. Каждое скачивание требует подтверждения (ADR-0017 §21–28) |
| `upload_file` | Копирование файла из локального каталога передачи на хост. **Выключен по умолчанию**: задайте `WINRIG_ALLOW_FILE_UPLOAD=true`, иначе сервер не объявляет инструмент и вызвать его нельзя. Инструмент хеширует локальный файл и показывает SHA-256 в подтверждении. Он отправляет байты окнами по 4 МиБ во временный файл. Каждое окно идёт через стандартный ввод команды на хосте. Хост хеширует этот файл до переименования. Цель подчиняется `WINRIG_WRITE_ALLOW_PATHS`, а существующая цель требует `overwrite`. Каждая загрузка требует подтверждения (ADR-0017 §26) |

Каждое подтверждение называет хост сеанса, пользователя запроса и инструмент. Оно называет цель и операцию с деталями, доступными до вызова, и содержит одну простую строку, которая сообщает эффект и можно ли операцию отменить. Скрытое значение показано только как `hidden`: старое и новое значения `set_registry` и содержимое `write_file` — скрытые значения. Текст команды и текст скрипта показываются целиком, без лимита в 200 символов, потому что оператор подтверждает то, что запустится. `kill_process` не читает командную строку вовсе. Сервер очищает каждое поле и ограничивает остальные поля 200 символами; обрезанный путь сохраняет хвост, а обрезанное поле несёт маркер `...` внутри лимита. Текст английский и не зависит от языка хоста. Файловые операции показывают разрешённые источник и цель, размер или счётчики и состояние перезаписи.

`write_file` отвергает защищённые пути тем же списком, что охраняет удаление. Он отвергает существующий файл, если не задан `overwrite`. Перед подтверждением хост сообщает, куда на самом деле ляжет файл и где у него стоят системные каталоги (`SystemRoot`, `ProgramFiles`, `ProgramFiles(x86)`, `ProgramData`, профили пользователей). Поэтому Windows на томе, отличном от `C:`, защищена так же.

Инструмент отвергает путь с 8.3-именем (`PROGRA~1`): сравнить его со списком может только хост. Административный общий ресурс `\\host\C$\...` инструмент проверяет как `C:\...`. Общие ресурсы `ADMIN$`, `PRINT$`, `SYSVOL` и `NETLOGON` защищены целиком. Точки повторной обработки (junction и symlink) в родительских каталогах цели инструмент не раскрывает (ADR-0015). Оператор может разрешить запись под защищённым корнем списком `WINRIG_WRITE_ALLOW_PATHS` (ADR-0017). Такой элемент снимает отказ для `write_file` и `delete_file`. Тогда подтверждение несёт предупредительную строку с именем класса. Список никогда не снимает отказ по 8.3-имени. Он также не снимает отказ символической ссылки или junction: операция подействовала бы на цель ссылки. Путь тома устройства (`\\?\Volume{...}`, `\\?\GLOBALROOT`) и существующий каталог как цель тоже отвергаются. Аудит записывает элемент, который разрешил защищённый путь.

Содержимое идёт кусками по ~1,5 КБ, потому что командная строка WinRS ограничена примерно 8191 символом. Инструмент отвергает путь настолько длинный, что его команды не влезут в эту строку. Предел — около 530 символов для UTF-8 и около 470 символов для остальных кодировок, для пути без символа кавычки. Поэтому инструмент годится для конфигураций и скриптов, а не для больших объёмов. Остаток ограничивает `WINRIG_MAX_WRITE_BYTES` (по умолчанию 64 КиБ). Куски ложатся во временный файл рядом с целевым файлом. Переименование заменяет целевой файл. Сбой на середине оставляет существующий файл нетронутым.

Это ограничение на длину относится к командной строке, а не к выводу. Скрипт, который не влезает в одну команду, запишите через `write_file` и затем запустите по пути. Команда остаётся короткой, каким бы длинным ни был скрипт.

`run_command` выключен по умолчанию. Задайте `WINRIG_ALLOW_COMMAND_EXEC=true`, чтобы сервер объявил его. Инструмент запускает одну команду PowerShell. Оператор подтверждает её, и подтверждение показывает полный текст команды. Сервер кодирует текст команды как base64-строку UTF-16. Затем он декодирует строку в блок скрипта на хосте. Кавычка или терминатор в тексте поэтому не могут выйти за пределы сгенерированной обёртки. Команда должна влезть в одну командную строку WinRS, поэтому текст содержит не более 979 символов. Более длинный скрипт запишите через `write_file` и запустите по пути, либо через `run_script`. Сервер отвергает команду вне непустого `WINRIG_ALLOWED_COMMANDS` до сетевой активности. Список — это набор префиксов, сравнение без учёта регистра после обрезки пробелов. Пустой список допускает любую команду. Список не образует границу. Ведущие `&`, `.` и `powershell -c` начинаются с текста, которого в списке может не быть. Псевдоним, оператор вызова и закодированная команда делают то же. Любой текст после разрешённого префикса выполняется. Поэтому `;`, перевод строки, `|` и `$(...)` не возвращают управление списку. Элемент `&` или `.` сам по себе допускает всё. Скрипт, записанный через `write_file` и затем запущенный, тоже обходит его (ADR-0013 §18). Список защищает от случайной команды, а не от намерения. При включённом `run_command` и пустом списке защита путей остальных инструментов перестаёт быть гарантией продукта. То же относится к подтверждению остальных модифицирующих операций. Они остаются свойствами отдельных инструментов. Это осознанный выбор оператора (ADR-0013, Q-14).

`run_script` выключен по умолчанию. Задайте `WINRIG_ALLOW_SCRIPT_EXEC=true`, чтобы сервер объявил его. Он запускает скрипт PowerShell длиннее одной командной строки WinRS. Сервер записывает скрипт во временный `.ps1` в каталоге временных файлов сеанса кусками, читает файл и выполняет его текст как блок скрипта, затем пытается удалить файл. У скрипта нет `$PSScriptRoot`, нет `$PSCommandPath` и нет аргументов. Сервер показывает SHA-256 скрипта в подтверждении и записывает его в аудит, и он сверяет хеш до запуска. Одно подтверждение покрывает всю операцию и показывает весь скрипт построчно, без лимита в 200 символов. Список префиксов `WINRIG_ALLOWED_COMMANDS` не фильтрует скрипт, потому что сервер не может осмысленно проверить текст скрипта по префиксу. Подтверждение это сообщает. Скрипт подчиняется `WINRIG_MAX_WRITE_BYTES`, а вывод — тем же лимитам, что у `run_command`. Результат несёт `temp_file` с исходом очистки и `warning`, когда временный файл может остаться. Инструмент может отказать, если скрипт не даёт вывода 60 секунд (ADR-0017 §29–34).

Файловые операции `copy_file`, `move_file`, `rename_file` и `create_directory` выключены по умолчанию. Задайте `WINRIG_ALLOW_FILE_OPS=true`, чтобы сервер объявил их. `copy_file` копирует файл или каталог. Копирование каталога рекурсивно, и подтверждение показывает счётчики файлов, каталогов и байтов. Копирование обходит исходное дерево один раз и отвергает его, если в нём есть символическая ссылка или junction; команда повторяет проверку во время выполнения. `move_file` переименовывает объект на одном томе, а между томами копирует файл, сверяет размер и затем удаляет источник. Перемещение каталога между томами отвергается, потому что подразумеваемое рекурсивное удаление попадает под DR-6; скопируйте каталог и удалите источник двумя вызовами. `rename_file` меняет последний компонент в том же каталоге и принимает одно новое имя: разделитель, зарезервированное имя устройства (`CON`, `NUL`, `COM1`, ...) и точка или пробел в конце отвергаются. `create_directory` создаёт конечный каталог и каждого недостающего родителя; подтверждение показывает число созданных уровней и самый верхний создаваемый уровень, который тоже проходит границу записи. Цель каждого инструмента подчиняется списку `WINRIG_WRITE_ALLOW_PATHS`; источник копирования только читается, поэтому он может лежать в системном каталоге. Ни один из четырёх не заменяет существующий каталог, а существующая цель требует `overwrite` (кроме `create_directory`, который её отвергает). Инструменты обращаются к хосту классами `[IO.File]` и `[IO.Directory]`, поэтому шаблон в пути не раскрывается. Частичное копирование или перемещение — это ошибка, а не успех. Долгое копирование или перемещение может отказать, если не даёт вывода 60 секунд. Цель или источник, доступные только для чтения, дают понятную ошибку: у инструмента нет `-Force`, и он никогда не снимает атрибут «только чтение». Перезапись сохраняет список управления доступом и атрибуты заменяемого файла. `write_file` тоже использует разрешённый хостом .NET-путь для своих кусков.

`download_file` выключен по умолчанию. Задайте `WINRIG_ALLOW_FILE_DOWNLOAD=true`, чтобы сервер объявил его. Он читает файл на хосте и пишет его в локальный каталог передачи. Сначала инструмент читает размер и время изменения источника. Он отвергает файл выше `WINRIG_MAX_TRANSFER_BYTES` (по умолчанию 256 МиБ) до чтения. Подтверждение показывает разрешённый удалённый путь, размер, время изменения и локальное назначение. Хеш оно не показывает: до чтения он неизвестен. Затем инструмент читает файл окнами по 16 МиБ через необработанный канал, строками base64 по 1 МиБ. Вывод идёт непрерывно, поэтому большой файл не даёт тайм-аут, а весь файл никогда не грузится в память хоста. Хост читает с разделяемым доступом на чтение и удаление, поэтому файл, открытый другим процессом (живой журнал), всё равно копируется. Инструмент хеширует байты по мере чтения. После последнего окна отдельный проход на хосте хеширует ровно прочитанную длину и сверяет два дайджеста. Расхождение или короткий файл — это отказ с текстом «the source changed during the transfer». Инструмент пишет окна во временный файл рядом с конечным путём. Сбой или отмена удаляют этот файл, поэтому частичный файл не остаётся. Результат несёт имя, размер и хеш, а не содержимое. Локальный каталог — `WINRIG_TRANSFER_DIR`, по умолчанию подкаталог `transfer` каталога состояния. В HTTP-режиме сервер изолирует каждого пользователя в подкаталоге его канонической идентичности (DR-3). Каталог и его файлы используют приватные режимы (`0700`/`0600`). Инструмент принимает одно простое локальное имя файла. Он отвергает разделитель, компонент `..`, ведущую точку, зарезервированное имя устройства, символическую ссылку и управляющий или форматный символ. Существующий локальный файл требует `overwrite`. Источник-каталог, символическая ссылка или junction отвергаются. Источник в системном каталоге допускается, и подтверждение предупреждает об этом. Каждое скачивание требует подтверждения, потому что переносит данные с хоста. Аудит записывает разрешённые пути, размер, оба хеша и состояние подтверждения. Содержимое он не записывает (ADR-0017 §21–28).

`upload_file` выключен по умолчанию. Задайте `WINRIG_ALLOW_FILE_UPLOAD=true`, чтобы сервер объявил его. Он копирует файл из локального каталога передачи на хост. Инструмент принимает одно простое локальное имя файла и абсолютный удалённый путь. Он читает только из каталога пользователя запроса (DR-3). Он отвергает символическую ссылку, любой объект кроме обычного файла и файл, доступный другому пользователю на запись. В Unix он также отвергает файл с несколькими жёсткими ссылками. В Windows инструмент не видит жёсткую ссылку, поэтому держите каталог передачи приватным. Он отвергает файл выше `WINRIG_MAX_TRANSFER_BYTES` (по умолчанию 256 МиБ) до чтения. Инструмент хеширует локальный файл один раз. Подтверждение показывает локальный источник, разрешённый удалённый путь, размер, SHA-256, состояние перезаписи и эффект. Удалённая цель подчиняется границе `write_file`. Защищённый путь отвергается, если его не покрывает `WINRIG_WRITE_ALLOW_PATHS`; тогда подтверждение предупреждает. Существующая цель требует `overwrite`. После подтверждения инструмент отправляет файл окнами по 4 МиБ. Каждое окно — одна команда на хосте, а байты приходят на её стандартный ввод, а не в текст команды. Поэтому предел командной строки WinRS примерно в 8191 символ не ограничивает размер окна. Первое окно создаёт временный файл рядом с конечным путём и отвергает существующий файл. Каждое следующее окно должно найти временный файл ожидаемой длины. Инструмент хеширует байты ещё раз при отправке. Он останавливается, если дайджест отличается от подтверждённого, например когда локальный файл изменился после подтверждения. Последняя команда на хосте хеширует временный файл и сверяет дайджест с подтверждённым. Затем она проверяет цель и каждый родительский каталог на символическую ссылку или junction и ставит файл переименованием (атомарная замена при `overwrite`). Расхождение или сбой до размещения удаляют временный файл и оставляют цель прежней. Отмена останавливает команду на хосте и удаляет временный файл. Отмена или потерянный ответ во время размещения могут прийти после замены. Тогда цель в неизвестном состоянии, аудит записывает `unknown`, и оператор должен проверить файл. Если хост недоступен для удаления, ошибка называет временный файл. Результат несёт имя, удалённый путь, размер и хеш. Аудит записывает два пути, размер, оба хеша и состояние подтверждения, но не содержимое (ADR-0017 §26, §38).

Клиент без elicitation по умолчанию отказывает модифицирующей операции, потому что у подтверждения нет канала. Оператор может задать `WINRIG_CONFIRM_FALLBACK=proceed`, чтобы операция всё же выполнилась, и тогда аудит помечает запуск как выполненный без подтверждения. Послабление срабатывает только когда клиент не объявил канал. Отказ пользователя, отмена, тайм-аут и ошибка транспорта никогда не обходятся (ADR-0013 §19–23, TR-SEC-11).

## Установка

К каждому релизу приложены готовые бинари для Linux, macOS и Windows. Рядом с каждым архивом лежит контрольная сумма `sha256`. Linux-бинари собраны со статической линковкой (musl), поэтому не требуют определённой версии glibc.

```bash
# Замените версию и таргет на свою платформу.
curl -LO https://github.com/fgbm/winrig/releases/latest/download/winrig-v0.2.0-x86_64-unknown-linux-musl.tar.gz
curl -LO https://github.com/fgbm/winrig/releases/latest/download/winrig-v0.2.0-x86_64-unknown-linux-musl.sha256
sha256sum -c winrig-v0.2.0-x86_64-unknown-linux-musl.sha256
tar xzf winrig-v0.2.0-x86_64-unknown-linux-musl.tar.gz
install -m 0755 winrig ~/.local/bin/winrig
```

Архивы называются `winrig-v<версия>-<таргет>`, где таргет — один из `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin` или `x86_64-pc-windows-msvc`. На macOS архив `aarch64` — для Apple Silicon, `x86_64` — для Intel. Подходят и `tar`, и `unzip`, потому что в архиве рядом с бинарём лежат `LICENSE` и `README.md`.

Чтобы собрать из исходников, см. [Быстрый старт](#быстрый-старт).

## Быстрый старт

Соберите один раз:

```bash
cargo build --release
```

Создайте шифрованный профиль. Команда читает пароль без эха и печатает токен профиля ровно один раз:

```bash
./target/release/winrig setup corp --user 'DOMAIN\user'
```

Команда печатает токен профиля и JSON-определение MCP-сервера. Либо вставьте определение в клиент вручную, либо дайте `setup` записать его за вас. `setup` обновляет конфигурацию клиента на месте и не трогает чужие записи:

```bash
./target/release/winrig setup corp --user 'DOMAIN\user' --write-config opencode --scope global
./target/release/winrig setup corp --user 'DOMAIN\user' --write-config claude-code --scope project
```

`--write-config` требует уровень. Передайте `--scope global` для пользовательской конфигурации или `--scope project` для текущего репозитория. Без флага `setup` спрашивает в терминале. В неинтерактивном запуске (скрипт, CI) `setup` отказывает и указывает на `--scope`.

По умолчанию сервер подключается только к loopback (`localhost`, `127.0.0.0/8`, `::1`). Хосты, к которым он может ходить, задаёт `--allowed-hosts`: список через запятую; элемент с ведущей `.` — суффикс домена; `*` — любой хост. `setup` пишет его в запись клиента как `WINRIG_ALLOWED_HOSTS`, а повторный `setup` без флага эту переменную убирает:

```bash
./target/release/winrig setup corp --user 'DOMAIN\user' --write-config claude-code --scope global --allowed-hosts '.corp.example,web-01'
```

Запись называется так же, как та, что уже обслуживает этот профиль. Поэтому повторный `setup` обновляет её на месте, а не добавляет вторую. Это важно: две записи на один профиль поднимают два процесса. Второй теряет блокировку профиля и выходит, а клиент сообщает лишь `MCP error -32000: Connection closed`. Когда профиль ещё никем не обслуживается, имя — `winrig`. `--server-name` задаёт его явно.

Поддерживаемые клиенты: `opencode`, `claude-code`, `codex`, `cursor`. Project-уровень находит ближайший каталог-предок с `.git` (с откатом к текущему каталогу) и пишет в `<root>/opencode.json`, `<root>/.mcp.json`, `<root>/.codex/config.toml` или `<root>/.cursor/mcp.json`. Global-уровень сохраняет пользовательские пути.

Для opencode `setup` пишет токен профиля в отдельный файл `0600` и подставляет его ссылкой `{file:...}`. Поэтому токен профиля никогда не лежит внутри конфигурации клиента. На project-уровне этот файл живёт в `WINRIG_STATE_DIR`, а не в репозитории. Для остальных трёх клиентов токен профиля идёт в конфигурацию клиента значением. На project-уровне такой файл обычно коммитится, поэтому `setup` печатает предупреждение, а `winrig` выставляет файлу `0600` на Unix.

Запустите сервер в одном из двух режимов:

```bash
# Локальный stdio-процесс для одного клиента (токен профиля приходит из окружения клиента)
WINRIG_TOKEN='<токен из setup>' ./target/release/winrig stdio --profile corp

# HTTP-сервис на 127.0.0.1:8005/mcp для нескольких проектов
WINRIG_TOKEN='<токен из setup>' ./target/release/winrig serve --profile corp

# Переопределить адрес из командной строки (важнее окружения)
./target/release/winrig serve --profile corp --port 9000 --host 0.0.0.0

# Передать секреты аргументами вместо окружения (важнее окружения)
./target/release/winrig serve --profile corp --token '<токен из setup>'
./target/release/winrig serve --auth-token '<общий секрет>'
```

Флаги `--token` и `--auth-token` перекрывают `WINRIG_TOKEN` и `WINRIG_AUTH_TOKEN`. Секрет, переданный аргументом, виден в списке процессов. Поэтому предпочитайте окружение или конфигурацию клиента, где это возможно.

Определение сервера, которое печатает и записывает `setup`, включает `WINRIG_TOKEN`, `WINRIG_PROFILE_DIR` и `WINRIG_STATE_DIR`. Поэтому клиент находит профиль даже при нестандартных каталогах.

Чтобы оставить путь по заголовкам вместо профиля, задайте общий секрет и обойдитесь без профиля:

```bash
echo "WINRIG_AUTH_TOKEN=$(openssl rand -base64 32)" >> .env
set -a; . ./.env; set +a
./target/release/winrig serve
```

В HTTP-режиме привязка по умолчанию — `127.0.0.1:8005`, конечная точка — `/mcp`. Серверу нужен хотя бы один секрет. Он отказывает в старте, если нет ни токена профиля, ни `WINRIG_AUTH_TOKEN`.

## Профили

```bash
winrig setup corp --user 'DOMAIN\user'   # создать; печатает токен профиля один раз
winrig setup corp --user 'DOMAIN\user' --overwrite   # заменить существующий профиль
winrig list                              # таблица: NAME, USER, PATH; секретов нет
winrig list --json                       # те же данные в JSON
winrig rotate corp                       # перешифровать под свежим токеном профиля
winrig forget corp                       # удалить профиль (идемпотентно)
winrig doctor                            # сравнить настройки winrig-серверов; только чтение
```

`doctor` читает конфигурации всех четырёх клиентов и обоих уровней. Он перечисляет каждый winrig-сервер с действующими значениями известных настроек: `WINRIG_ALLOWED_HOSTS`, `WINRIG_ALLOW_INSECURE_TLS`, `WINRIG_ALLOW_FILE_WRITE` и остальных переменных `WINRIG_*`. Отсутствующая настройка показывается со своим значением по умолчанию и пометкой `(default)`. Команда сравнивает серверы и помечает каждую настройку, по которой они расходятся. Значение печатается только для известных настроек; любая другая переменная показывается как `set` или `empty`, поэтому значение токена не раскрывается. Служебные переменные уровня сервера (`WINRIG_TOKEN`, `WINRIG_PROFILE_DIR` и остальные переменные идентичности) показываются, но не сравниваются: они различаются между серверами по замыслу. Запись winrig, которая не относится к stdio-серверу, например HTTP-запись, показывается как `not compared` и не влияет на код возврата. Команда ничего не записывает. Код возврата 0, когда серверы согласны, 1, когда они расходятся, файл конфигурации пропущен или запись не разобрана, и 2 при ошибке использования.

Файл профиля — `corp.json` в каталоге профилей. В нём лежат версия формата, каноническое имя учётной записи, соль HKDF-SHA256, nonce XChaCha20-Poly1305 и шифртекст. Имя учётной записи связано как associated data. На Unix права файла — `0600`, права каталога — `0700`. Более широкие права дают предупреждение, а не отказ. Журнал различает неверный токен профиля и повреждённый файл, но клиенту оба отвечают 401. Если `WINRIG_AUTH_TOKEN` совпал с токеном профиля, старт отказывает.

Учётная запись имеет вид `DOMAIN\user`, например `contoso\alice`. Деление для NTLM повторяет `spnego` (движок `requests-ntlm`, который использовал Python-сервер): система делит имя по первому обратному слэшу. UPN (`user@realm`) или голое имя остаются целыми с пустым доменом. Профиль хранит учётную запись в каноническом нижнем регистре, и то же значение уходит на хост. NTLM сам приводит имя пользователя к верхнему регистру, когда строит хеш. Поэтому регистр домена на результат не влияет.

Один процесс на профиль. Lock-файл в каталоге состояния профиля останавливает второй процесс на том же профиле. Второй процесс отказывает и указывает на HTTP-режим. Изменения профиля на диске вступают в силу при следующем старте. Пароль профиля по-прежнему подчинён блокировке учётной записи AD. Если его отвергли дважды в разных окнах блокировки, профиль отказывает до перезапуска процесса. Выполните `setup` заново.

### Безопасность транспорта

`winrig` отдаёт открытый HTTP на `/mcp`, TLS-слушателя в бинаре нет. **Bearer-токен теперь ключ: кто его перехватит, тот достигнет сервера и расшифрует пароль AD.** Не привязывайтесь к не-loopback адресу без TLS-терминирующего обратного прокси впереди (nginx, Caddy или ingress). Адрес по умолчанию — `127.0.0.1` именно поэтому.

Многопользовательское развёртывание предполагает, что прокси аутентифицирует клиентов. Прокси передаёт заголовки `Authorization`, `X-AD-User` и `X-AD-Password` без изменений. Удалённый участок WinRM отдельный: используйте `use_ssl` или порт 5986, когда хоп до Windows-хоста должен быть шифрованным. Не включайте `WINRIG_ALLOW_INSECURE_TLS=true`, если самоподписанный сертификат не выбран сознательно.

Список хостов по умолчанию пропускает только loopback. Иначе агент, получивший инструкцию из данных, мог бы подключиться к хосту атакующего и отдать ему NTLMv2-ответ доменной учётной записи.

Поверх открытого HTTP этот участок WinRM шифрован лишь частично. `winrm-rs` запечатывает SOAP-тела ключом сессии NTLM. Но ключа не существует, пока не завершится рукопожатие. Поэтому **первый** запрос на каждом новом соединении несёт своё тело открытым текстом рядом с сообщением Type 3. Запечатаны только последующие запросы на этом keep-alive соединении.

Для `winrig` первое тело — это shell `Create`, а не скрипт. Но если хост отвечает на незашифрованное сообщение пустым `HTTP 500` (`AllowUnencrypted=false`, умолчание Windows), он сразу отвергает этот запрос. Порт 5986 снимает и экспозицию, и отказ.

## Настройка клиента

Есть две формы запроса. С **токеном профиля** секрет — это токен профиля, а идентичность берётся из профиля, поэтому `X-AD-User` не нужен. С **общим секретом** запрос обязан нести `WINRIG_AUTH_TOKEN` и `X-AD-User`. Сервер проверяет токен прежде, чем доверяет `X-AD-User`: этот заголовок — ключ кэша паролей и сессий в памяти.

`WINRIG_AUTH_TOKEN` обязателен только на пути по заголовкам. `X-AD-Password` необязателен на уровне HTTP, но на пути по заголовкам обязателен для каждого `connect`. Закэшированный пароль по одному имени сессию не открывает, потому что `X-AD-User` может назвать любой держатель общего секрета. Уже открытая сессия исполняет команды без повторного пароля, пока не закрыта (ADR-0015). Пароль приходит заголовком, а не диалогом: `winrig` не запрашивает пароли через elicitation. Спецификация MCP исключает из elicitation секреты, а ревизия протокола `2026-07-28` убирает elicitation целиком (см. `docs/adr/0006-password-header-and-confirmation.md`).

Пути ниже — пользовательские, их записывает `--scope global`. При `--scope project` та же запись идёт в проектный файл, перечисленный в [«Быстром старте»](#быстрый-старт).

### opencode (`~/.config/opencode/opencode.json`)

`setup --write-config opencode --scope global` пишет этот файл. Токен профиля подставляется из приватного файла:

```json
{
  "mcp": {
    "winrig": {
      "type": "local",
      "command": ["/path/to/winrig", "stdio", "--profile", "corp"],
      "environment": { "WINRIG_TOKEN": "{file:~/.config/opencode/winrig-token}" },
      "disabled": false
    }
  }
}
```

### Claude Code

`setup --write-config claude-code --scope global` пишет блок `mcpServers` файла `~/.claude.json`. Эквивалент через CLI:

```bash
claude mcp add winrig -- /path/to/winrig stdio --profile corp
```

### Codex (`~/.codex/config.toml`)

`setup --write-config codex --scope global` пишет его:

```toml
[mcp_servers.winrig]
command = "/path/to/winrig"
args = ["stdio", "--profile", "corp"]

[mcp_servers.winrig.env]
WINRIG_TOKEN = "<токен из setup>"
```

### Cursor (`~/.cursor/mcp.json`)

`setup --write-config cursor --scope global` пишет блок `mcpServers`. HTTP-форма работает одинаково для любого клиента: направьте клиент на streamable-HTTP конечную точку и передайте `Authorization: Bearer <token>`.

Любой другой MCP-клиент работает так же. Либо используйте stdio-определение, которое напечатал `setup`, либо направьте клиент на HTTP-конечную точку. Передайте токен профиля в качестве bearer.

### Подтверждения на клиентах без elicitation

Модифицирующие инструменты получают подтверждение через MCP elicitation. Они **отказывают (fail-closed)**, когда клиент не может спросить. opencode 1.18.31 объявляет только `roots`. Поэтому модифицирующие инструменты отказываются там работать и говорят об этом, а не действуют без подтверждения. Инструменты только для чтения работают нормально. Замену канала (`input_required`, SEP-2322) проект отслеживает в `docs/ROADMAP.md` и `docs/QUESTIONS.md` Q-10.

`WINRIG_CONFIRM_FALLBACK=proceed` меняет это. Настройка позволяет модифицирующей операции выполниться, когда клиент не объявил канал elicitation. Аудит помечает запуск как выполненный без подтверждения. Настройка снимает fail-closed со всех модифицирующих инструментов сразу, включая удаление. В клиентах со своей системой разрешений разрешение заменяет подтверждение. При `permission: "*": "allow"` никто не подтверждает. Комбинация `proceed` + `WINRIG_ALLOW_COMMAND_EXEC=true` + пустой `WINRIG_ALLOWED_COMMANDS` + разрешение клиента `allow` выполняет произвольные команды. Человек в таком запуске не участвует. Ни одна из четырёх настроек не включена по умолчанию (ADR-0013 §23, Consequences). В HTTP-режиме настройка действует для каждого клиента без elicitation, потому что winrig решает по объявленным возможностям запроса.

## Журналирование

`WINRIG_LOG_DIR` хранит `winrig.log` и аудит `winrig-audit.log`. Сервер создаёт каталог `0700`, а файлы `0600`, и переприменяет права при каждой ротации.

Аудит записывает каждый вызов с текстом PowerShell и выдержкой из его вывода. В этом выводе могут быть содержимое файлов, данные реестра, списки учётных записей и сертификаты. Поэтому по умолчанию аудит пишет только первые `WINRIG_AUDIT_MAX_OUTPUT_CHARS` символов. Агент всё равно получает полный ответ.

Задайте `WINRIG_AUDIT_LOG_BODY=0`, чтобы писать только метаданные вызова. Отказ политики до обращения к хосту идёт отдельной записью `POLICY REFUSED`. Запись несёт пользователя, инструмент, код и причину. Отказ политики бывает при неразрешённом хосте, порте или TLS, при `connect` без `X-AD-Password` и на защищённом пути. Запись, которую список `WINRIG_WRITE_ALLOW_PATHS` разрешил в защищённом месте, идёт отдельной записью `WRITE ALLOWED BY ALLOWLIST` с именем разрешившего элемента (ADR-0017 §39).

В stdio-режиме stdout несёт только JSON-RPC. Журнал сервера и аудит уходят в stderr и в каталог состояния профиля. Поэтому клиент, который запускает `winrig stdio`, никогда не видит строк журнала, подмешанных в протокол.

## Разработка

```bash
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
cargo deny check
cargo build --release
```

Закреплённый тулчейн лежит в `rust-toolchain.toml`. CI выполняет те же команды плюс `cargo-audit` и сборку на MSRV (`rust-version` в `Cargo.toml`). Живого Windows-хоста в окружении разработки нет. Тесты работают на фиктивном `WinRmTransport`, который записывает переданные ему команды, и сети не касаются. `tests/http_gate.rs` проверяет реальную обвязку axum+rmcp `/mcp`, а `tests/stdio_mode.rs` запускает настоящий бинарь поверх stdio. Канон проекта, требования, ADR и цикл ревью живут в `AGENTS.md` и `docs/`.

### Релизы

Релиз ставится так: поднимите `version` в `Cargo.toml`, добавьте соответствующую запись в `CHANGELOG.md` и отправьте тег `vX.Y.Z`. Тег запускает `.github/workflows/release.yml`. GitHub Release создаётся из записи changelog, а бинарь собирается под пять таргетов и прикладывается с контрольной суммой `sha256`. Workflow отказывает, если тег и версия в `Cargo.toml` расходятся.

| Workflow | Триггер | Что делает |
|----------|---------|--------------|
| `ci.yml` | каждый push и pull request | `fmt`, `clippy`, `test`, release-сборка, сборка на MSRV, `cargo-audit`, `cargo-deny` |
| `release.yml` | тег `vX.Y.Z` | пишет GitHub Release и загружает архивы платформ с контрольными суммами |
