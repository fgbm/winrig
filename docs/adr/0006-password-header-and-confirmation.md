# ADR-0006 — Пароль AD через заголовок, elicitation только для подтверждения

- Статус: принято
- Дата: 2026-09-19
- Связано: ADR-0001, ADR-0002, DR-1, DR-4, DR-5

## Контекст

Python-версия запрашивала пароль AD через MCP elicitation. Спецификация MCP прямо указывает, что elicitation не предназначен для секретов, PII и учётных данных; кроме того, в ревизии протокола `2026-07-28` elicitation исключён, и на таком клиенте ввод пароля становится невозможен. Элицитация как канал подтверждения модификаций (булево согласие) остаётся допустимой.

## Решение

1. Пароль AD поставляется заголовком `X-AD-Password` и хранится только в памяти с idle-TTL. Отдельного запроса пароля через elicitation нет.
2. Модифицирующие операции подтверждаются elicitation-запросом формы `{ "confirm": bool }`; подтверждением считается только явное `true`.
3. При недоступности elicitation модифицирующая операция не выполняется и возвращает ответ с полем `error` (fail-closed, DR-5).

## Последствия

- Требование `X-AD-Password` делает клиентский setup немного подробнее, но снимает зависимость от ревизии протокола и не проводит секрет через диалог.
- Подтверждение остаётся каналом, который можно отозвать на стороне клиента, не ослабляя read-only инструменты.
- Это отличие от Python-версии: там пароль можно было ввести интерактивно; здесь — только заголовком.

## Уточнение (ADR-0009)

Пароль можно не передавать в каждом запросе: `winrig setup` один раз принимает его через CLI и шифрует в профиль, ключ которого хранится у клиента. В режиме профиля `X-AD-Password` не нужен, а `X-AD-*` игнорируются. Требование «секретов через elicitation нет» сохраняется: пароль вводится в CLI, а elicitation остаётся только каналом подтверждения.
