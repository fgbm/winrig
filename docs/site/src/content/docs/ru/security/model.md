---
title: Модель безопасности
description: Как winrig аутентифицирует каждый запрос, держит секреты в памяти и защищает разрушительные операции.
---

winrig администрирует Windows-хосты по WinRM и держит пароль AD в памяти. Bearer-токен — это ключ, который одновременно даёт доступ к серверу и расшифровывает пароль AD. Эта страница описывает защиты, которые применяет сервер.

## Аутентификация до доверия

Каждый запрос обязан предъявить один из двух секретов. Общий `WINRIG_AUTH_TOKEN` использует путь по заголовкам и требует `X-AD-User`. Токен профиля расшифровывает файл профиля. Совпадение `WINRIG_AUTH_TOKEN` с токеном профиля останавливает старт. Сервер не стартует без хотя бы одного секрета ([ADR-0001](https://github.com/fgbm/winrig/blob/main/docs/adr/0001-shared-secret-and-request-identity.md)).

## Идентичность на каждом запросе

В HTTP секрет текущего запроса задаёт пользователя, в чьём имени работает инструмент. Токен профиля задаёт идентичность профиля и заставляет сервер игнорировать `X-AD-*`. Общий секрет требует `X-AD-User`. Идентичность не наследуется от задачи, создавшей сессию MCP. В stdio идентичность равна профилю процесса.

Сервер проверяет токен прежде, чем доверяет `X-AD-User`: этот заголовок — ключ кэша паролей и сессий в памяти. Кэш паролей и кэш сессий изолированы по пользователю ([ADR-0001](https://github.com/fgbm/winrig/blob/main/docs/adr/0001-shared-secret-and-request-identity.md)).

## Секреты только в памяти

Пароли и парольные фразы не попадают в журналы, аудит и конфигурацию и не попадают в коммит. На диске лежит только аутентифицированный шифртекст профиля, а ключ на сервере отсутствует. Секрет, который несёт команда, не должен появиться в аудите ни в каком виде ([ADR-0002](https://github.com/fgbm/winrig/blob/main/docs/adr/0002-secrets-confirmation-deletion.md), [ADR-0008](https://github.com/fgbm/winrig/blob/main/docs/adr/0008-injection-redaction-delete-and-confirmation.md)).

Файл профиля — `corp.json` в каталоге профилей. В нём лежат версия формата, каноническое имя учётной записи, соль HKDF-SHA256, nonce XChaCha20-Poly1305 и шифртекст. Имя учётной записи связано как associated data. На Unix права файла — `0600`, права каталога — `0700`.

## Подтверждение, fail-closed

Каждая модифицирующая операция требует явного подтверждения оператора; без канала подтверждения операция не запускается. Модифицирующие инструменты получают подтверждение через MCP elicitation и отказывают (fail-closed), когда клиент не может спросить ([ADR-0006](https://github.com/fgbm/winrig/blob/main/docs/adr/0006-password-header-and-confirmation.md)). Подтверждение называет хост, пользователя и инструмент, а также цель и эффект. Скрытое значение показано только как `hidden`: старое и новое значения `set_registry`, содержимое `write_file` и командная строка `kill_process` остаются скрытыми, и сервер очищает каждое поле и ограничивает его 200 символами.

:::caution
Пароль приходит заголовком, а не диалогом. winrig не запрашивает пароли через elicitation. Спецификация MCP исключает из elicitation секреты, а ревизия протокола `2026-07-28` убирает elicitation целиком.
:::

## Защищённые пути и разрушительные операции

Рекурсивное удаление отвергает корни томов и системные каталоги в любой форме пути. Оно отвергает и точки повторной обработки (junction или symlink). `write_file` отвергает защищённые пути тем же списком, что охраняет удаление ([ADR-0002](https://github.com/fgbm/winrig/blob/main/docs/adr/0002-secrets-confirmation-deletion.md), [ADR-0015](https://github.com/fgbm/winrig/blob/main/docs/adr/0015-security-defaults-and-host-resolved-paths.md)).

Перед подтверждением хост сообщает, куда на самом деле ляжет файл и где у него стоят системные каталоги. Поэтому Windows на томе, отличном от `C:`, защищена так же. Административный общий ресурс `\\host\C$\...` инструмент проверяет как `C:\...`, а общие ресурсы `ADMIN$`, `PRINT$`, `SYSVOL` и `NETLOGON` защищены целиком.

## Список разрешённых хостов и TLS по умолчанию

Список разрешённых хостов и запрет на понижение проверки TLS настраиваются через окружение ([ADR-0004](https://github.com/fgbm/winrig/blob/main/docs/adr/0004-environment-configuration.md), [ADR-0015](https://github.com/fgbm/winrig/blob/main/docs/adr/0015-security-defaults-and-host-resolved-paths.md)).

- По умолчанию сервер подключается только к loopback: `localhost`, `127.0.0.0/8`, `::1`. Сервер не разрешает имена через DNS.
- `WINRIG_ALLOW_INSECURE_TLS` по умолчанию `false`: сервер отвергает `verify_cert=false` до любой сетевой активности.
- Неверный элемент в `WINRIG_ALLOWED_HOSTS` (например `*.corp.example`) останавливает старт.

:::danger
Не разрешайте любой хост без причины. Агент может получить инструкцию из данных и подключиться к хосту атакующего. Такой вызов отдаёт атакующему NTLMv2-ответ доменной учётной записи.
:::

## Безопасность транспорта

winrig отдаёт открытый HTTP на `/mcp`, TLS-слушателя в бинаре нет. Bearer-токен теперь ключ: кто его перехватит, тот достигнет сервера и расшифрует пароль AD.

:::danger
Не привязывайтесь к не-loopback адресу без TLS-терминирующего обратного прокси впереди (nginx, Caddy или ingress). Адрес по умолчанию — `127.0.0.1` именно поэтому.
:::

Многопользовательское развёртывание предполагает, что прокси аутентифицирует клиентов. Прокси передаёт заголовки `Authorization`, `X-AD-User` и `X-AD-Password` без изменений.

Удалённый участок WinRM отдельный: используйте `use_ssl` или порт 5986, когда хоп до Windows-хоста должен быть шифрованным. Поверх открытого HTTP этот участок WinRM шифрован лишь частично. `winrm-rs` запечатывает SOAP-тела ключом сессии NTLM, но ключа не существует, пока не завершится рукопожатие. Поэтому первый запрос на каждом новом соединении несёт своё тело открытым текстом рядом с сообщением Type 3. Но если хост отвечает на незашифрованное сообщение пустым `HTTP 500` (`AllowUnencrypted=false`, умолчание Windows), он сразу отвергает этот запрос. Порт 5986 снимает и экспозицию, и отказ.
